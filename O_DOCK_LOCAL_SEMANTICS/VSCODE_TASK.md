# VS Code Codex에 보낼 구현 지시

> 제공받은 스타터의 당시 제안이다. 현재 상태는 IMPLEMENTATION.md 및 ../docs/reports/LOCAL_SEMANTICS_20261111.md를 확인한다. 아래 v4·6,158개·미연결 상태는 최신 상태가 아니다.

현재 프로젝트 소스와 PROJECT_STRUCTURE.md, 최근 작업 보고서를 먼저 읽고 실행 가능한 오픈소스 기반 번역·분류 경로를 구현하라. 이 폴더는 독립 로컬 추론 스타터이며 기존 v4 코드의 자동 교체 패치가 아니다.

## 확정된 현황

- 사용자 제공 최신 보고서: 상품 6,158개, duplicate_hidden 1,555건, 의미 결과 ready 3 / partial 2, 대기열 0.
- 대기열 0은 전체 번역 완료가 아니다. 기존 상품을 모두 등록한 적이 없다.
- semantic_provider / semantic_rules / semantic_policy / semantic_queue로 책임을 나누었다.
- 현재 규칙 버전은 ja-ko-semantics-v4-fields. 필드별 게시·보류, 수동 이름 보존, 계정별 개인 기록과 관리자 인증이 있다.
- 이미지 중복·권한·개인 기록 관련 과거 미완료 지시를 다시 실행하지 않는다.
- 상품 수집 시 과거 자동 유료 이름 번역 경로를 제거한 상태다.

## 1. 실행 기반

1. 현재 머신 nvidia-smi와 Docker GPU 인식 확인. 과거 사용자 보유 장비 RTX 5060 Ti 16GB가 지금 PC에도 있다고 가정하지 마라.
2. O_DOCK_LOCAL_SEMANTICS/compose.yaml로 별도 Ollama를 실행한다. 기존 DB·media 볼륨은 건드리지 않는다.
3. qwen3:8b Q4_K_M 기준으로 모델을 내려받고 로컬 health와 기본 5개 preview를 실행한다.
4. 이미지 digest와 모델 digest, 양자화·context·프롬프트·규칙 버전을 기록한다. latest 이미지는 초기 실행용이며 운영 재현성을 위해 확인한 digest로 고정한다.
5. 이 환경에서 GPU가 없거나 모델 실행이 불가능하면 정확한 원인과 필요한 환경만 보고하고 모델 실행 성공을 꾸미지 않는다. 유료 API로 자동 전환하지 않는다.

## 2. 기존 앱에 공급자 통합

- 기존 semantic_provider의 현재 인터페이스를 읽고 provider 선택을 추가한다. 모델 I/O와 검증 규칙은 분리한다.
- 권장 설정 예: SEMANTIC_PROVIDER=ollama, SEMANTIC_MODEL=qwen3:8b, SEMANTIC_BASE_URL=http://host.docker.internal:11434. 실제 프로젝트 설정 규약에 맞게 통합하고 연결을 직접 확인한다.
- 로컬의 /api/chat, stream=false, think=false, JSON Schema를 사용한다. 일반 텍스트를 억지 정규식으로 JSON처럼 적용하지 않는다.
- 키가 없는 로컬 모델 호출에 GMS/OpenAI 키 필수 검사를 적용하지 않는다.
- 기존 원문 근거 검증, 필드별 게시, 관리자 권한, source hash 검증과 대기열 상태 전이를 그대로 거친다.
- 모델만 교체하면 기존 캐시를 쓰는 문제를 막기 위해 provider/model digest/prompt/schema/input/rules 버전을 캐시 키에 반영한다. 검증만 바뀌었을 때 원 응답 재사용 경로는 유지한다.
- 원문, raw 응답, 검증 후 필드, 보류 사유, 모델·사전 버전, 입력 잘림 여부를 구분하여 저장한다. 다른 모델의 기존 응답을 덮어쓰지 않는다.
- 타임아웃·메모리 부족·출력 잘림·JSON 오류는 모델 실패로 남기고 게시하지 않는다. 공급자 장애를 null 필드 정상 성공으로 기록하지 않는다.
- 컨텍스트를 넘는 설명은 작업 목적별로 선별하고 선택 근거·원문 위치를 기록한다. 본문 첫 문장만 무조건 사용하는 정규식을 범용 분류기로 간주하지 않는다.
- GPU는 동시 작업 1개부터. 서버가 계속 켜져 있어도 관리자에 의한 제한 배치/대기열 소비로 시작하며 일반 사용자 조회가 추론을 유발하지 않게 한다.
- 스타터의 LOCAL_PREVIEW_NOT_APPLYABLE 보고서는 기존 apply에 직접 넣지 마라. 실제 앱 입력/source hash를 기반으로 정식 CLI가 생성한 보고서를 사용한다.

## 3. 번역과 분류의 역할

- 원문에서 제작사(기존 DB), 브랜드/라인, 작품, 제품 주인공, 형태 근거를 분리한다.
- 추출한 작품·캐릭터 원문을 검증된 한국어 alias/관계 사전과 대조한다.
- 확인된 이름을 사용해 한국어 상품명을 일관되게 구성하되 버전/숫자/코드를 유지한다.
- null이 정당한 굿즈·오리지널 캐릭터도 평가한다. 모든 상품에 같은 필수 분류를 강제하지 않는다.
- TENITOL을 soft_vinyl로 분류하거나 スケール感을 numeric scale로 읽는 기존 오류를 회귀 사례로 넣는다.
- 프리렌 상품 각주의 페른, 페른 설명에 나온 스승 프리렌을 상품 캐릭터로 추가하지 않는다.
- 마왕짱/베르주/베르너 같은 과거 모델 출력을 공식명 정답이라고 가정하지 않는다.

## 4. 평가 후 확대

최초 5개는 연결 확인용이다. 제조사·작품·브랜드·상품군이 다른 50~100개를 정답 라벨링하고, 일부는 끝까지 모델 선택에 쓰지 않는 고정 평가셋으로 남긴다. 숫자는 초기 목표이며 이미 확보된 정답 수가 아니다.

지표: JSON 성공률, 작품/캐릭터 정규화 정확도, 다인 캐릭터 precision/recall, 형태 macro F1, 무근거 게시율, 미확정 필드 비율, 번역 오역·누락·숫자 보존, 처리 시간·GPU 메모리. 초기 로딩 시간과 정상 반복 추론 시간을 따로 잰다. ready 비율을 정확도로 부르지 마라.

정확도가 부족하면 사전/입력/검증을 먼저 진단한다. 추가 모델과 비교할 때 같은 정답셋을 사용한다. 큰 모델이 무조건 더 정확하다고 단정하지 않는다. 통과한 소규모 보고서를 apply하고 UI를 확인한 후 100개 이하 배치로 확대한다. 전체 상품을 처음부터 무검토 게시하지 않는다.

## 5. 파인튜닝은 정답셋 이후

1. 사람이 검수한 JSONL과 근거를 모은다. 과거 모델 출력의 ready 상태만 보고 정답으로 쓰지 마라.
2. 동일 SKU/URL·재판·이름 변형·설명 복제는 같은 split에 둔다. 가능하면 작품/제품 라인 단위로 평가 누수를 막는다.
3. base/프롬프트/alias만 사용한 기준점과 비교할 데이터를 준비한다.
4. 실제 GPU와 지원되는 CUDA/PyTorch/PEFT 조합을 확인한 뒤 QLoRA SFT를 별도 학습 환경에서 진행한다. 운영 backend에 학습 의존성을 섞지 않는다.
5. 학습 어댑터는 기준 모델 revision, 데이터/설정 hash와 함께 버전 관리한다. held-out 성능이 개선된 경우에만 배포한다.
6. 학습이 완료되지 않았는데 “O_DOCK 전용 모델 학습 완료”라고 보고하지 않는다.

기존 PostgreSQL/Chroma를 테스트 저장소로 쓰지 말고, 키를 비운 격리 테스트에서 provider mock·기존 필드별 정책·권한·개인 기록 회귀 검증을 수행하라. 완료 시 실제 모델 실행 여부, 평가 결과, 앱 연결 여부, 아직 안 된 학습을 구분해 보고하라.
