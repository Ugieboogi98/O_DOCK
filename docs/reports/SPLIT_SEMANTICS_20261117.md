# 사전 우선 번역·분류 분리 파이프라인 · 2026-11-17

## 구성

`수집·원문 저장 → 번역 대기열 → 상품명 번역 → 상품 분류 → 원문 기반 검증 → 유효한 필드 저장`

기존 Qwen3 8B 한 번의 호출로 번역·분류를 함께 하던 처리를 분리했다. 새 가중치를 학습하거나 파인튜닝한 작업은 아니다. 기존 로컬 기반 모델 두 종류에 역할별 입력·프롬프트·출력 스키마·캐시·검증 단계를 구축했다.

| 단계 | 처리 |
|---|---|
| 사전 조회 | 검증된 동일 맥락 상품명, 작품·캐릭터 별칭, 상품 용어를 우선 사용 |
| 번역 | Qwen3 8B, 상품명만 입력. 설명 문서 전체를 번역 입력으로 보내지 않음 |
| 번역 복구 | 단순 번역이 검증에 실패하면 원문 전체를 덮는 조각 번역과 모델 자체 검토. 그래도 실패하면 반영하지 않음 |
| 분류 | 사전으로 해결되면 모델 호출 생략. 나머지는 Qwen3 1.7B에 원문 필드·근거 발췌·번역 힌트 제공 |
| 검증 | 전체 원문에서 근거 확인, 숫자·스케일·모델 코드·미번역 문자 확인, 기존 필드 검증과 수동 분류 유지 |

[분류 모델 공식 배포 페이지](https://ollama.com/library/qwen3:1.7b). 외부 유료 API로 자동 전환하지 않는다. 설명문 번역의 기존 별도 경로는 유지하며, 이번 분리 처리기의 주 번역 대상은 상품명이다.

## 보유 자료 조사와 사전

`data/reference/semantic_dictionary/catalog.json`에 기존 지식을 통합했다.

- 작품 규칙 1,135행, 기본 캐릭터 규칙 252행. 기존 보조 별칭·작품 문맥 규칙도 함께 재사용한다.
- 재사용 가능한 정확한 상품명 번역 4,655개. 제조사·작품·제품 라인이 일치해야 재사용한다.
- 참조 JSON 14개와 매칭·정규화 코드 4개의 SHA-256을 기록한다.
- 기존 원문과 검증 프로필의 해시가 현재 일치하는지 확인한다. 단순히 name_ko가 채워져 있다는 이유로 사전에 넣지 않는다.
- 새 분리 모델의 추측을 자동으로 사전에 승격하지 않는다. 이전 사전에 이미 승인돼 있던 동일 결과만 유지할 수 있다.
- 제목이 같아도 맥락이나 번역이 충돌하면 자동 재사용에서 제외한다.
- `versions/{fingerprint}.json`에 사전 스냅샷을 남긴다. 기존 표기의 검증은 자동 규칙 기반이며 공식 한국어명 인증이나 독립적인 사람의 검수를 뜻하지 않는다.

시행 중 발견한 개선: 에리스의 상품명 약칭을 무직전생 문맥 안에서만 연결하고, Desktop Cute·차이나 드레스 버전·온라인 한정·REBOOT 표현을 보완했다. 수집기의 NFKC 정규화와 사전 표기 차이도 함께 처리한다.

## 저장과 복구

- 번역·분류 캐시를 별도로 저장한다. 키는 원문, 사전 버전, 모델 digest, 단계, 프롬프트와 파이프라인 버전을 포함한다.
- 번역 20건을 처리한 후 분류를 처리한다. 상품마다 두 모델을 반복 교체하는 횟수를 줄인다.
- 컨텍스트는 각 역할 4,096. 긴 문서의 분류 근거는 문자 그대로 발췌하며, 검증은 원본 전체에서 한다.
- 상품 하나의 오류는 다음 상품 진행을 막지 않는다. 실패 원문·제안·실패 단계를 보고서에 남긴다.
- 같은 실패는 1시간 뒤 재시도한다. 사전 또는 파이프라인 버전이 바뀌면 즉시 재시도할 수 있다.
- 모델 서버 연결이 끊기면 30초 간격으로 기다린다. 저장한 단계 캐시는 재연결 후 재사용한다.
- 처리할 대상이 0개여도 재시도 대기가 있으면 `waiting_retry`로 구분한다.
- 이름·분류가 전부 확정된 경우만 ready다. 알려진 필드만 저장한 partial과 실패를 완료로 혼동하지 않는다.

## 실행 경로

호스트의 기본 소비자와 Compose semantic-worker를 새 분리 소비자로 연결했다. 현재 실행 방식은 호스트다. 호스트와 Compose 소비자를 동시에 실행하지 않는다. 서로 다른 파일 시스템의 잠금만으로 중복 실행을 완전히 막을 수 없기 때문이다.

```powershell
# 로컬 모델 서버가 꺼져 있을 때
docker start odock-ollama-cpu-20261117

# 기존 처리기를 중지한 상태에서 사전 갱신
.\.venv\Scripts\python.exe tools/run_split_semantics.py --build-dictionary

# 기본 큐 소비
.\.venv\Scripts\python.exe -u tools/run_split_semantics.py --watch --limit 20 --report-dir data/private/semantics/split_queue_20261117

# 특정 상품만 재검증
.\.venv\Scripts\python.exe tools/run_split_semantics.py --limit 2 --ids 6820 6821 --report-dir data/private/semantics/manual_recheck
```

모델 역할은 `--translation-model`, `--classification-model`로 지정할 수 있다. 기본 설정은 `semantic_translation_model=qwen3:8b`, `semantic_classification_model=qwen3:1.7b`다. `.env` 비밀정보는 출력하거나 변경하지 않았다.

## 실패 상품 자동 재시도 중지 · 16:41

사용자 요청에 따라 현재 호스트 소비자를 `--skip-failed` 옵션으로 재시작했다. 실패 기록이 있는 대기 상품은 자동 재시도에서 제외하며 나머지 상품만 처리한다. 상품·실패 원인·DB 대기 작업을 삭제하거나 완료로 표시하지 않는다. 사전·파이프라인 버전이 변경돼도 이 옵션을 사용하는 동안 실패 기록이 있는 상품은 건너뛴다.

- 제외 내역: `data/private/semantics/split_queue_20261117/skipped_failures.json`.
- 상태의 `skipped_failed`는 보류 수이며, 남은 작업이 전부 실패 보류이면 `paused_failed`로 표시한다.
- 새로 처리하는 상품이 실패하면 이후 자동 선택에서 제외한다.
- 특정 상품은 `--ids`로 명시하면 재검사할 수 있다. 전체 자동 재시도를 재개하려면 기존 처리기를 종료하고 `--skip-failed` 없이 실행한다.
- 새 로그: `worker.skip_failed.stdout.log`, `worker.skip_failed.stderr.log`.
- 관련 테스트 21개 통과. Docker의 일회성 백엔드 검사 환경을 사용했으며 운영 DB 데이터 변경 검사는 수행하지 않았다.

현재 정책으로 재개:

```powershell
.\.venv\Scripts\python.exe -u tools/run_split_semantics.py --watch --skip-failed --limit 20 --report-dir data/private/semantics/split_queue_20261117
```
