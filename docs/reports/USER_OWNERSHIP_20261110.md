# 계정 로그인과 개인 기록 소유권 — 2026-11-10

## 사용 방법

- 상단 로그인(`/login`)에서 계정을 만들거나 로그인한다. 사용자 이름은 영문·숫자와 일부 구분문자 3–40자이며 대소문자를 구분하지 않는다. 비밀번호는 12–128자다.
- 로그인한 계정의 관심상품과 구매·배송 기록만 조회·등록·수정·삭제할 수 있다.
- 기존 관심상품은 데이터 현황(`/status`)에서 기존 ADMIN_TOKEN으로 관리자로 연결하면 확인할 수 있다. 예약된 admin 계정은 일반 회원가입이나 비밀번호 로그인으로 생성·접속할 수 없다.
- 일반 계정 로그인은 공용 카탈로그 수정 권한을 주지 않는다. 기존 공용 카탈로그 관리자 토큰 인증은 별도로 유지한다.

## 서버 구현

- User, UserSession 테이블과 `20261110_users` 마이그레이션 추가.
- 비밀번호는 무작위 salt와 scrypt로 해시한다. 서버는 세션 토큰 원문 대신 SHA-256 해시를 저장한다.
- 로그인 세션은 HttpOnly / SameSite=Lax / Path=/api 쿠키로 전달하며 유효기간은 7일이다. 로그아웃 시 서버 세션을 삭제한다.
- 계정 비밀번호 인증 5회 실패 시 15분 잠금. 다른 Origin의 계정·개인 기록 수정 요청은 차단한다.
- 모든 개인 기록 API는 서버에서 인증한 user_id를 사용한다. 다른 소유자의 구매 ID를 지정하면 404다. 관리자 토큰도 관리자 자신의 개인 기록만 조회하며 일반 계정의 기록을 우회 조회하지 않는다.
- Favorite는 (figure_id, user_id) 복합 PK로 바꾸어 여러 사용자가 같은 상품을 찜할 수 있다. 중복 등록은 DB on-conflict 처리로 방지한다.
- Purchase는 user_id FK와 인덱스를 추가했다. 기존 구매 ID·금액·상품 버전은 변경하지 않는다.
- 공개 카드에 개인 찜 여부를 기본 포함하지 않는다. 계정별 목록·상세에서만 해당 사용자의 찜 여부를 조회한다.
- 이미지 파일을 제외한 API 응답은 Cache-Control: no-store로 설정했다.

## 화면의 계정 전환

- 로그인/로그아웃 및 관리자 연결 변경 시 개인 찜 상태와 비교 목록을 초기화한다. 이전 계정의 늦은 조회·찜 수정·로그인 상태 확인 응답은 새 계정에 반영하지 않는다.
- 초기 찜 조회 중 계정이 바뀌면 이전 클릭으로 새 계정의 찜을 변경하는 요청도 보내지 않는다.
- 계정 전환 시 구매 목록과 수정 중인 양식을 초기화한다. 비로그인 상태에는 로그인 안내를 표시한다.
- 탭에 다시 포커스하면 서버의 현재 로그인 상태를 확인한다. 일반 계정은 같은 브라우저의 쿠키 세션을 공유한다.
- 브라우저에 저장하는 AI 대화도 계정별 키로 분리했다. 기존 소유자 미지정 대화 키는 관리자 계정에서만 사용하며 다른 계정이나 비로그인 화면에 로드하지 않는다. 대화가 서버 계정 데이터로 이관된 것은 아니다.

## 검증 및 반영

- 백엔드 관련 테스트 **139개 통과**. 마지막 쿠키 속성 검증 추가 후 소유권 테스트 **4개 재통과**.
- 프런트엔드 **31개 통과**, 최종 Docker production build 성공.
- 별도 PostgreSQL 복원본에서 회원가입, 시퀀스의 관리자 ID 충돌 방지, 같은 상품의 독립된 찜, 상대방 구매 수정/삭제 404, 일반 계정 수집 요청 403, 로그아웃 후 401을 검증했다.
- 운영 Nginx 경유 검증: 비로그인 찜/구매 조회 401, 관리자 자신의 기존 찜 2건 조회, 공개 상세의 비개인 상태, health, no-store 헤더 정상.
- 운영 DB에는 테스트 일반 계정이나 구매 데이터를 생성하지 않았다. 적용 후 계정은 기존 기록의 관리자 소유자 1개다.
- duplicate_hidden 1,555건 유지. 수집·모델 API 호출·seed 재실행 없음.
- 마이그레이션 동안 backend를 잠시 중지하고 백업을 받았다. init/worker는 기동하지 않았다.
- 브라우저 렌더링 육안 검증은 수행하지 않았다. 화면 로직 단위 테스트·Vue 빌드·서버 API와 PostgreSQL 통합 검증을 수행했다.

## 복구 자료와 범위

- 수정 전 소스: `backups/user_ownership_20261110/`.
- 복원/이관 실험 DB: `odock_users_test_20261110_1612`.
- 적용 전 데이터 비교용 DB: `odock_users_baseline_20261110_1616`.
- 두 검증 DB는 운영과 별개이며 현재 로컬 PostgreSQL에 보존했다.
- 복합 소유권을 예전 단일 소유자 구조로 되돌리면 다중 사용자의 같은 상품 찜이 충돌할 수 있어 자동 downgrade를 금지했다. 복구가 필요하면 신규 개인 데이터 내보내기와 백업 복원 계획을 먼저 마련한다. 단순 소스 되돌리기만으로 기존 스키마와 호환된다고 가정하지 않는다.
- 비밀번호 변경/재설정, 사용자 관리 UI, 외부 배포 운영은 아직 구현하지 않았다. 현재 HTTP localhost 쿠키 설정이며 HTTPS 운영에서는 AUTH_COOKIE_SECURE=true를 적용해야 한다.
- Git 저장소가 아니므로 커밋하지 않았다.
