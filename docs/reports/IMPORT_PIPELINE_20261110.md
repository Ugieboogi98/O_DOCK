# 제조사별 가져오기와 의미 검증 대기열 통합

작성일: 2026-11-10 (Asia/Seoul)

## 완료한 작업

후류·S-FIRE·타이토의 오프라인 importer와 반다이 한국몰 저장 경로를 공통 의미 검증 대기열에 연결했다. 외부 입력의 원문은 보존하고, 한국어 파생 정보는 기존 필드별 검증·게시 경로를 사용한다. 자동 모델 호출은 추가하지 않았다.

공통 처리 함수는 `backend/app/services/import_pipeline.py`의 `commit_import()`다.

1. 입력으로 추가·변경한 DB 행을 flush한다. autoflush를 끄는 후류 importer도 같은 규칙을 따른다.
2. 상품의 제조사·제품 라인 관계를 다시 읽어 변경 전 캐시를 사용하지 않도록 한다.
3. 현재 원문 문맥의 source hash로 기존 의미 결과를 확인한다.
4. 검증이 필요하면 대기 작업을 만들거나 기존 pending 작업을 재사용한다.
5. 원문 DB 행과 대기 작업을 같은 트랜잭션으로 커밋한다.

유효한 의미 결과가 있으면 새 작업을 만들지 않는다. 원문이 바뀌면 새 해시로 재검증 대상을 기록한다. 이전 입력에 대한 결과가 최신 원문 작업을 완료 처리하지 못하는 기존 검사는 유지한다.

## 경로별 반영

| 경로 | 유지한 저장 단위 | 변경 |
|---|---|---|
| import_furyu_bundle.py | 입력 묶음 전체 | 충돌 없이 처리된 상품을 모아 한 트랜잭션에서 대기 작업과 함께 저장 |
| import_sfire_bundle.py | 상품별 | 각 성공 상품의 원문과 대기 작업을 함께 저장 |
| import_taito_bundle.py | 상품별 | 각 성공 상품의 원문과 대기 작업을 함께 저장 |
| services/bnkr_catalog.py | 상품 메타데이터·설명·가격 | 같은 저장 경로 사용. 기존 이미지 보강 단계는 유지 |

기존 제조사 식별·URL/JAN/SKU 충돌·버전 보존 규칙은 변경하지 않았다. preview와 validate는 작업을 등록하지 않는다.

보고서에는 `semantic_pending`, `semantic_cached` 수치가 추가된다. pending은 현재 대기 상태로 준비한 상품 수이며, 이미 존재하는 pending 작업을 재사용한 경우도 포함한다. 새 작업 개수나 번역 완료 개수와 같은 뜻이 아니다.

## 재가져오기 이미지 보호

타이토 importer가 같은 variant/source URL의 이미지 행을 항상 personal_local로 바꾸던 경로를 수정했다. 기존 상태가 duplicate_hidden이면 원래 행과 URL을 유지하고 복사를 건너뛴다. 파일 누락 상태여도 숨김 결정을 취소하지 않는다.

이는 같은 source URL의 재노출 방지다. 다른 URL이나 다른 해상도로 새로 들어온 유사 이미지 전부를 비교·차단하는 기능은 아니다.

## 검증

- 백엔드 전체 테스트 **174개 통과**, 건너뜀 없음.
- 신규 importer 통합 테스트 **13개**는 SQLite에서도 통과했고, 전체 테스트에서는 운영과 별개인 PostgreSQL 테스트 DB의 상품별 임시 스키마에서 다시 실행했다.
- 세 오프라인 importer와 반다이 한국몰 preview에서 상품·대기 작업을 만들지 않는 것을 확인했다.
- 반복 가져오기 시 pending 작업 재사용, 유효한 검증 결과 재사용, 원문 변경 시 새 해시의 작업 생성을 확인했다.
- 대기 작업 생성 오류를 주입해 원문 상품·설명 DB 저장이 함께 롤백되는 것을 확인했다.
- 원본/수동 한국어 이름, 상품·버전 ID, 관심상품과 구매 금액·연결 보존을 확인했다.
- 타이토 숨김 이미지가 재노출되지 않는 회귀 테스트를 추가했다.
- 모의 제공자 호출 금지 장치를 사용했고, 테스트용 벡터 저장소도 운영과 분리했다.
- 구조 검사 오류 0건. 최종 실행 이미지의 기존 HTTP 계약 40개 경로가 동일했다.

DB 트랜잭션의 원자성을 검증한 것이며 이미지 파일 복사까지 하나의 트랜잭션으로 되돌린다는 의미는 아니다. 이미지 파일 보관과 복구 정책은 기존 동작을 유지했다.

## 운영 반영과 실제 상태

backend만 재빌드·반영했다. DB 스키마 변경, init/seed/worker 기동, 실제 상품 재가져오기, 웹 수집, 유료 모델 호출은 실행하지 않았다.

반영 후 상태:

- 상품 6,158개.
- 의미 레코드 ready 3 / partial 2.
- 운영 검증 대기 작업 0건.
- duplicate_hidden 이미지 1,555건.
- health 정상.

대기 0건은 새 경로를 운영 데이터에 소급 실행하지 않았기 때문이다. 다음 실제 import commit부터 공통 경로를 사용한다. 기존 전 상품을 임의로 대기열에 등록하지 않았다.

## 사용 절차

1. `python scripts/import_bundle.py <furyu|s_fire|taito> validate`
2. 필요하면 같은 명령의 모드를 preview로 바꾸어 DB 충돌을 확인한다.
3. 검토 후 명시적으로 commit한다. 호스트 실행기의 기존 백업·덤프 검증 절차는 유지된다.
4. `product_semantics pending`으로 작업을 확인한다.
5. 별도로 승인한 제한된 `run --queued --limit ...`에서 모델 응답을 만들고, 보고서 검토 후 apply한다.

마지막 단계의 run은 유료 호출을 할 수 있다. 이번 작업에서는 운영 대기 작업 실행이나 기존 5개 레코드 재저장을 수행하지 않았다. 기존 저장명과 원문 메타데이터의 표시 우선순위도 바꾸지 않았다.

## 복구 자료와 후속 과제

- 변경 전 importer와 반다이 저장 서비스: `backups/import_pipeline_20261110/`.
- 이번 변경에는 DB 마이그레이션이 없어 소스 복구에 전체 DB 복원은 필요하지 않다.
- 원복 시 보존본을 원래 위치에 복원하고 backend를 재빌드한다. 새 경로로 생성된 대기 작업을 임의로 지우지 않는다.
- 초기 seed, 별도 수동 보강·복구 도구 전체를 이번 공통 commit 경로로 바꾼 것은 아니다. 무조건 모든 원문을 재등록하거나 번역하지 않는다.

다음 독립 과제는 이미지의 실제 표본 검토와 URL 변경 중복 방지, 출처 있는 한국어 alias·번역 정확도 평가, 상품명 변경 이력, 큰 화면 컴포넌트 분리와 검색 지연 시간 분석이다.
